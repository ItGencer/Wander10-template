# Coding Rules

## Загальні Правила

- Не створювати реальні секції, стилі або скрипти з цього дизайн-опису без окремого запиту на реалізацію.
- Усі інструкції й дизайн-планування тримати в `doc/`.
- Майбутній вихідний код тримати в `src/`.
- Стилі тримати в `src/style/`.
- Асети тримати в `src/assets/`.
- Використовувати тільки Node.js/npm для налаштування, запуску і збірки проєкту.

## HTML

- Використовувати семантичні елементи: `header`, `nav`, `main`, `section`, `article`, `figure`, `footer`.
- На сторінці має бути один основний `h1`.
- Не додавати стартові header, hero, cards, footer або SEO-метадані в початковий `src/index.html`, якщо користувач просить тільки старт або тільки інструкції.
- Початковий `src/index.html`, якщо його створюватимуть пізніше, має бути мінімальним пустим шаблоном із правила `frontend-doc-agent`.

## BEM

- Для авторських класів використовувати BEM: `block`, `block__element`, `block--modifier`.
- Назви мають описувати зміст компонента, а не зовнішній вигляд.
- JavaScript-хуки краще робити через `data-*`, а не через стилізаційні класи.

## SCSS

- Використовувати SCSS і `@use`.
- Токени кольорів, шрифтів, радіусів і відступів винести в окремі partial-файли після старту реалізації.
- Не робити глибоке вкладення селекторів.
- Не створювати CSS-секції з дизайн-опису до окремого запиту на верстку.

## JavaScript / TypeScript

- Тип скриптів: `[NEEDS CONFIRMATION]`.
- Для JavaScript використовувати ES modules.
- Для TypeScript увімкнути strict-налаштування.
- Інтерактивні патерни, якщо будуть потрібні: мобільне меню, smooth scroll, фільтр/акордеон локацій, lazy behavior для карток.
- Станову логіку тримати в маленьких класах або модулях.

## Доступність

- Усі кнопки та посилання мають мати зрозумілі назви.
- Контраст тексту на фото hero має бути перевірений після вибору реального зображення.
- Для змістовних фото потрібен описовий `alt`.
- Декоративні зображення отримують пустий `alt`.
- Фокус-стани для клавіатури мають бути видимими.
